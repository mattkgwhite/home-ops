# Kubernetes volume storage plan

This plan is for review. Apply the changes in separate stages so each workload can be verified before its previous storage is retired.

## Recommendation

Move Gotify to the existing PostgreSQL instance, `cluster01`, and put Gotify’s files on the existing Hetzner Storage Box. Review the three released Hetzner disks before consolidating other live workloads. Keep the active Loki volume at 20 GiB for now.

On 19 November 2026, Olumpus had six active `hcloud-volumes` claims with 70 GiB provisioned and about 6.58 GiB in use. The available Prometheus samples from the preceding 30 days showed peaks of about 0.62 GiB for PostgreSQL and 0.75 GiB for Loki. Gotify supports PostgreSQL through `GOTIFY_DATABASE_DIALECT=postgres`. The migration imports the records from the 68 KiB SQLite file into a dedicated `gotify` database. Gotify connects to `cluster01` over the network, and PostgreSQL stores the records on its existing 10 GiB claim. [Gotify database settings](https://gotify.net/docs/config#gotify-database-dialect)

| Change | Cloud Volume capacity reclaimed | Monthly saving at €0.69 per 10 GiB |
| --- | ---: | ---: |
| Retire the three released disks after checking their backing volumes and recovery value | 40 GiB | €2.76 |
| Move Gotify to `cluster01` and retire its original disk | 10 GiB | €0.69 |
| **Potential total** | **50 GiB** | **€3.45** |

The six active allocations cost €4.83 per month at the quoted rate. The Gotify migration would take active allocation from 70 GiB to 60 GiB and its cost to €4.14 per month. The €2.76 for released disks is additional and depends on their backing volumes still being billable. The estimates assume current Storage Box capacity covers Gotify’s files and backup copies.

## Storage decisions

- **MariaDB and MySQL.** BookStack is the only app found that requires either engine, and it has no live workload or PVC on Olumpus. When BookStack is deployed, use one MariaDB instance with one PVC. Give each compatible app its own logical database and scoped credentials. The database server manages the files in its data directory, and applications connect through an internal Kubernetes Service. MySQL InnoDB Cluster and MariaDB Galera are available for high availability across independent nodes. Replicas on the single worker, Athena (`talos-oc7-jd1`), would share its failure and add storage and operational cost. `cluster01` already demonstrates the single-instance model. [BookStack database requirements](https://www.bookstackapp.com/docs/admin/installation/#requirements) · [PostgreSQL manifest](../../kubernetes/argo/manifests/postgres.yaml) · [MySQL InnoDB Cluster](https://dev.mysql.com/doc/refman/8.0/en/mysql-innodb-cluster-introduction.html) · [MariaDB Galera quorum](https://mariadb.com/docs/galera-cluster/high-availability/understanding-quorum-monitoring-and-recovery)
- **Block and worker-local storage.** Keep dedicated block claims for PostgreSQL and Prometheus. Expanding an existing claim or provisioning a larger one still leaves PVCs scoped to their namespace and a Hetzner disk attachable to one worker at a time. Pooling unrelated workloads would require a different storage setup and make them share capacity and recovery. A Talos-local PV can save a new Cloud Volume allocation where recovery from backup or rebuild is acceptable. [Kubernetes PVC rules](https://kubernetes.io/docs/concepts/storage/persistent-volumes/#a-note-on-namespaces) · [Hetzner Volume limits](https://docs.hetzner.com/cloud/volumes/overview/) · [Talos user volumes](https://docs.siderolabs.com/talos/v1.14/configure-your-talos-cluster/storage-and-disk-management/disk-management/user)
- **Monitoring and RustFS.** Prometheus, Loki, and Alertmanager can share an `observability` claim while they run on the same node. Separate `subPath` directories would isolate their files, while free space and recovery would be shared. Defer that consolidation. Grafana already stores its application data in `cluster01`. RustFS needs its own data directory on a supported filesystem, which can be backed by a Cloud Volume or a Talos-local PV. RustFS classifies SMB/CIFS as unsupported. [Monitoring storage](../setup/monitoring.md) · [RustFS storage compatibility](../setup/rustfs.md#storage-compatibility)
- **Storage Box and S3.** Use the existing Storage Box for Gotify files and encrypted backup copies. Keep live SQL data directories on block or worker-local storage. Database durability depends on filesystem and caching guarantees as well as locking. At the quoted €8 per month, a new Object Storage subscription would cost more than the current active block allocation. Revisit it for workloads that use S3 directly or if backup requirements change. [Hetzner storage comparison](https://docs.hetzner.com/storage/general/which-storage-is-right-for-me/) · [Object Storage billing](https://docs.hetzner.com/storage/object-storage/overview/#pricing)

## Gotify migration

The live SQLite inventory showed one user and zero applications, clients, messages, or plugin records. The images and plugins directories were empty. Recheck the data after shutdown because the migration below assumes only the user record needs transfer.

### Stage and rehearse

1. Add a `gotify` prepared database and dedicated owner to `cluster01` using the existing PostgreSQL Operator pattern. Use the existing 1Password and External Secrets flow to provide `GOTIFY_DATABASE_CONNECTION` with TLS. Verify that Gotify’s credentials can create tables in its own database.
2. Confirm the `gotify` namespace exists, then sync the `gotify-files-smb` claim defined in `storage.yaml`. It uses `hetzner-storagebox-per-pvc`, which gives each claim its own directory on the same Storage Box. Verify that it binds and is writable by Gotify’s UID 1000. Keep the original `gotify-data` claim protected from Argo CD pruning and deletion during migration and rollback. [Storage manifest](../../kubernetes/argo/manifests/storage.yaml)
3. Rehearse against an isolated PostgreSQL database using the current Gotify image, `ghcr.io/gotify/server:3.1.1`. Let Gotify create its PostgreSQL schema. Verify the user transfer with a disposable fixture, including preservation of the password hash, ID, admin flag, creation time, optional OIDC ID, and the next generated user ID. If Gotify creates a temporary bootstrap user, remove that user in the same transaction as the import after verifying it is the only target row. Use the rehearsed import to preserve the original password hash without logging row contents. [Gotify manifest](../../kubernetes/argo/manifests/gotify.yaml) · [Gotify database initialization](https://raw.githubusercontent.com/gotify/server/v3.1.1/database/database.go) · [Gotify user model](https://raw.githubusercontent.com/gotify/server/v3.1.1/model/user.go)

### Cut over and verify

1. Set the Gotify deployment’s desired replica count to zero in Git and sync through Argo CD. Wait for its pod to terminate before reading the old claim. Capture a consistent SQLite backup and any files from `/app/data`, accounting for any SQLite journal files present. Run `PRAGMA integrity_check` on the backup and verify an encrypted off-worker copy can be read. Compare row counts with the rehearsal assumptions. If new data exists in the previously empty tables, restart Gotify on SQLite and revise the import to preserve those records before retrying. [Argo CD automated sync](https://argo-cd.readthedocs.io/en/stable/user-guide/auto_sync/)
2. Initialize the production `gotify` database with the same Gotify image in an isolated pod without a public route, then stop the pod. Run the rehearsed import into that database and advance the user ID sequence past the imported ID. Compare source and target row counts. Copy any application files found during the backup to the SMB claim, keeping the SQLite files in the backup and on the original claim.
3. Change Gotify’s Git values to use the `postgres` dialect, the ExternalSecret connection, and `gotify-files-smb` as its data claim. Restore the replica count to one and sync. Keep the existing image, Service, and route. Verify that Gotify is ready, the existing account can log in, a test message can be delivered and retrieved, and an uploaded icon survives pod replacement. Check that Gotify is using PostgreSQL and no longer mounts `gotify-data`.

### Roll back or retire the old disk

- Keep `gotify-data` and its underlying disk for seven days after a successful cutover. Before accepting new writes, roll back by restoring the SQLite configuration and original claim through GitOps. If new writes have been accepted, stop the application, export the PostgreSQL data and any new files, and reconcile them before switching back. The pre-cutover SQLite copy represents the point at which writes stopped.
- After the hold, verify a `gotify` PostgreSQL dump can be restored into an isolated database. Remove the original claim from the desired state, confirm no workload mounts it, and confirm the live PV’s Hetzner volume ID. Delete the claim and retire the retained backing disk as a separate cleanup action. Remove the stale PV record and verify the disk no longer appears in Hetzner inventory. [Cloud Volume retention configuration](../../kubernetes/argo/manifests/hcloud.yaml) · [Hetzner Volume backups and limits](https://docs.hetzner.com/cloud/volumes/overview/)

## Follow-up volume work

1. **Released volumes.** Check the old Vaultwarden (10 GiB), Vikunja (10 GiB), and Loki (20 GiB) PVs against their CSI volume IDs in Hetzner. Confirm the backing disks are detached, check that no live claim references those IDs, and verify any recovery copy still needed before approving retirement. The Kubernetes `Released` state alone does not establish that the disk still exists or can be deleted.
2. **Active Loki volume.** Keep `storage-loki-0` at 20 GiB. If resizing is revisited, confirm healthy ingestion, retention, and peak usage over a representative period. Reducing provisioned capacity requires a replacement claim and data migration if log history must be preserved. [Monitoring storage and retention](../setup/monitoring.md) · [Hetzner Volume resizing](https://docs.hetzner.com/cloud/volumes/faq/#can-i-resize-volumes)
